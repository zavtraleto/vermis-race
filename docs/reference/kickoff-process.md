# Кикофф: разработка игры на TypeScript + three.js с Claude Code

Nov 18, 2026 · @Maksim Boiarkin

## 1. Принципы

Агент сходится к правильному результату, только когда у него есть внешний оракул: тест, метрика, скриншот с критерием. Без оракула его «готово» означает лишь собственную уверенность. Второе ограничение: контекст заполняется быстро, и качество падает вместе с ним. Остальные правила выводятся из этих двух.

1. **Игра запускается и проверяется из CLI.** Тесты, скриншот, прогон ботом на N секунд должны быть командами. Чего агент не может запустить сам, тем он не может пользоваться автономно.
2. **Симуляция отделена от рендера.** Ядро тестируется без WebGL за миллисекунды, поэтому цикл «правка → проверка» короткий и дешёвый.
3. **Состояние воспроизводимо.** Seeded RNG, save/load с первого дня, изменения состояния только через сериализуемые команды. Агент возвращается в одно и то же состояние и сравнивает «до» и «после», не тратя ходы на воспроизведение.
4. **Решения живут в файлах, важные — в проверках.** Лестница: CLAUDE.md → правило по пути → skill → hook → скрипт, который отказывает. Чем дороже забытое решение, тем ниже его опускать: CLAUDE.md только советует, hook срабатывает детерминированно.
5. **Красный тест до кода; тесты и ревью делает не автор кода.** Тест — единственная спецификация, которую агент не может «интерпретировать». Сессия, написавшая код, пишет тесты так, чтобы они проходили; субагент с чистым контекстом не несёт её допущений.
6. **Зелёные тесты не означают играбельную игру.** Нужны quality gate по метрикам геймплея и регулярная игра руками на целевом устройстве.
7. **Маленькие диффы, чистый контекст.** Автоматическое ревью хорошо работает на маленьком диффе и посредственно на большом. Неудачная ранняя попытка влияет на всю дальнейшую сессию, поэтому дешевле начать заново.
8. **Минимальный обвяз.** Старт: 3 hooks, 3–4 skills, 2–4 субагента; остальное заводится после реальных инцидентов. Число агентов на результат почти не влияет, а на расход влияет сильно: в [замере yurukusa](https://dev.to/yurukusa/the-token-per-dollar-math-running-claude-max-for-30-days-2k1o) команда из 5 агентов потратила 27% дневного бюджета за 45 минут против 8% у одного агента с подзадачами.
9. **За человеком остаются:** каркас архитектуры, правила игры, game feel, финальный баланс, арт-направление.

Опорный кейс для большинства этих правил — [браузерный deckbuilder Eleven Labs](https://blog.eleven-labs.com/en/claude-code-workflow-kebab-roguelite/) на TypeScript: 9 дней, 93 PR, 1 087 тестов, весь код написан агентом.

## 2. Стек и структура репозитория

Стек: TypeScript (strict), three.js с зафиксированной точной версией, Vite, Vitest для ядра, Playwright для запуска и скриншотов, ESLint + Prettier, odiff для сравнения изображений. Версия three.js пинится, потому что агент иначе пишет под API той версии, которую помнит.

```
CLAUDE.md            короткий: версии, команды, жёсткие правила, где истина
.claude/
  rules/             sim.md, render.md, tests.md, assets.md (с paths:)
  agents/            reviewer.md, test-writer.md, playtest-critic.md
  skills/            next/, ship/, bot/, brief/
  settings.json      hooks + allowlist команд
docs/
  brief.md           GDD: пиллары, нумерованные правила, эталонный пример
  glossary.md        термин -> идентификатор в коде
  balance.md         дата, было, стало, почему, что измерено
  art-bible.md       палитра, свет, размеры, именование ассетов
  progress.md        что сделано, что следующее
  decisions/         ADR: одно решение на файл
src/
  sim/               чистая логика: state, commands, step, rng, systems
  data/              JSON с балансом и контентом + типы
  render/            three.js: сцена, меши, камера, шейдеры, эффекты
  input/             ввод -> команды
  ui/                HUD, меню
  app/               game loop, склейка, debug-интерфейс для тестов
tests/
  sim/               vitest
  e2e/               playwright: smoke, скриншоты
tools/               bot.ts, quality-gate.ts, shot.ts
shots/               эталонные скриншоты
```

Команды, которые должны существовать до первой фичи (имена условные):

| Команда | Что делает | Когда нужна |
| --- | --- | --- |
| `npm run check` | `tsc --noEmit` + eslint | День 0 |
| `npm test` | vitest по `src/sim` | День 0 |
| `npm run smoke` | production-сборка, Playwright прогоняет N кадров, ноль ошибок в консоли | День 0 |
| `npm run shot -- <сценарий>` | скриншот заданного состояния + odiff против эталона | День 0 |
| `npm run bot` | бот играет по сидам, пишет `results.json` | Когда появился игровой цикл |
| `npm run gate` | GO / CONDITIONAL / NO-GO по метрикам из `results.json` | Вместе с ботом |

## 3. Архитектура

Один поток данных в одну сторону: `input → Command → step(state, commands, rng) → state + events → render(state, events)`. Рендер читает состояние и никогда его не меняет.

**Ядро (`src/sim`)**

- Чистый seeded-reducer без движка: никаких импортов `three`, DOM и `src/render`. Запрет закрепляется линтером (`no-restricted-imports`), а не фразой в CLAUDE.md.
- Никаких `Math.random` и `Date.now`. Вся случайность идёт через один seeded RNG, чьё состояние лежит в `state`.
- Фиксированный шаг 1/60 с. В тестах время виртуальное: шаги вызываются явно, ввод подаётся на конкретных кадрах.
- `state` — плоский сериализуемый JSON. Из этого бесплатно получаются save/load, снимки для тестов и старт с любого состояния.
- Ввод игрока и ИИ превращается в сериализуемые команды. Это даёт реплей бага, скриптуемые сценарии и бота-плейтестера без отдельной инфраструктуры.
- Ядро возвращает список событий шага (попадание, смерть, подбор). Рендер и звук подписываются на события, а не на внутренности систем: связность ниже, агент меняет одну сторону, не зная другой.
- Мало типов сущностей: одна структура с полем `kind` вместо десятков классов, композиция вместо наследования. Ограничение: при тысячах объектов и жёстком бюджете кадра это тупик, там нужны ECS/SoA.

**Данные (`src/data`)**

- Баланс и контент лежат в JSON, в коде нет числовых литералов тюнинга. Правка цифр не трогает логику, поэтому баланс-итерации не требуют ревью кода.
- Каждое изменение цифр записывается в `docs/balance.md`.

**Рендер (`src/render`)**

- В `.claude/rules/render.md`: запиненная версия three.js и список удалённых API, которые агент склонен использовать по памяти.
- Бюджет draw calls и треугольников задан числом и читается из `renderer.info`; smoke-тест падает при превышении.
- Слои UI и геймплея переключаются флагом, чтобы скриншот проверял что-то одно.

**Debug-интерфейс для агента (`src/app`)**

- `window.gameState()` — JSON-снимок состояния; агент читает текст вместо того, чтобы угадывать по картинке.
- Запуск с заданным сидом и сценарием (например, параметры URL), промотка на N кадров, загрузка сохранения.

**Владение архитектурой.** Каркас задаёшь сам в первые 1–2 недели и читаешь каждый дифф ядра. Правку, которая ломает каркас, отклоняешь, даже если она работает: иначе через месяц код нельзя починить руками.

## 4. Документация и память проекта

Каждая сессия начинается с пустого контекста, поэтому память проекта — это файлы в репозитории, а не история чата.

| Файл | Что хранит | Правило |
| --- | --- | --- |
| `docs/brief.md` | Пиллары, нумерованные правила игры, эталонный пример, открытые вопросы, ограничения (платформа, бюджет кадра и бандла) | Источник истины. Правило меняется сначала здесь, потом в коде; иначе агент «чинит» игру в сторону своего представления о ней |
| `docs/glossary.md` | Термин → один идентификатор в коде | Без него каждая сессия изобретает синонимы |
| `docs/balance.md` | Дата, было, стало, почему, что измерено | Обновляется при каждой правке цифр |
| `docs/decisions/` | ADR: контекст, решение, последствия | Одно решение на файл; надёжнее единого MEMORY.md |
| `docs/progress.md` | Сделано, следующее, «промпт следующей сессии» | Обновляется в конце каждой задачи |
| `docs/art-bible.md` | Палитра, свет, размеры, именование и замена плейсхолдеров | Якорь стиля для любой генерации |
| `CLAUDE.md` | Версии, команды, жёсткие правила, где лежит истина | Меньше 100 строк (верхняя граница из документации — 200) |
| `.claude/rules/*.md` | Правила для конкретных папок с `paths:` | Грузятся только при работе с этими файлами и не занимают контекст в остальное время |

**Эталонный пример в brief.** Один полностью просчитанный сценарий с точным исходом (входное состояние, команды, ожидаемый результат числом). Он становится первым тестом и регрессионным якорем: при любой переделке механики исход остаётся прежним, пока ты сам не изменишь brief.

**Правила ведения CLAUDE.md**

- Только то, чего нельзя вывести из кода. Структуру кода не описывать.
- Каждая строка проходит вопрос: «вызовет ли её удаление ошибки?»
- После ошибки агента добавляется правило, которое её предотвращает; раз в неделю файл подрезается.
- Агент игнорирует правило по одной из двух причин: файл разросся и строка теряется, либо правило не допускает исключений и ему место в hook.

**Шаблон CLAUDE.md** (адаптировать под проект):

```
# <Name> — TypeScript (strict) + three.js <pinned version> + Vite
Truth: docs/brief.md (rules), docs/glossary.md (names), docs/balance.md (numbers).
Rule changes go to brief first, then code. Never invent game rules.

## Commands
- Check:      npm run check     (tsc --noEmit + eslint)
- Tests:      npm test          (vitest, src/sim)
- Smoke:      npm run smoke     (prod build, N frames, zero console errors)
- Screenshot: npm run shot -- <scenario>
- Bot + gate: npm run bot && npm run gate

## Hard rules
- src/sim imports nothing from three, DOM or src/render.
- No Math.random / Date.now in src/sim. All randomness via the seeded RNG in state.
- All state changes go through serializable commands.
- Tunable numbers live in src/data, never as literals.
- three.js: only the pinned version's API (see .claude/rules/render.md).
- Write the failing test first. Never modify a test to make it pass.
- Minimal diff. No new dependencies or abstractions without asking.
- Done = check + tests green, smoke clean, screenshot checked against the stated expectation.
```

## 5. Воркфлоу

Единица работы — вертикальный срез: одно правило или фича от ядра до экрана, один маленький PR.

**Цикл одной задачи**

1. `/clear`. Агент читает нужный раздел brief и затронутые файлы, код не пишет.
2. Plan mode. План сохраняется в файл или issue. План — дешёвая точка отката, а ошибка в архитектуре стоит дороже всего.
3. Красный тест на правило → убедиться, что падает → реализация → зелёный. Тесты менять запрещено.
4. `check` → `smoke` → скриншот или бот с заранее названным критерием приёмки.
5. Ревью диффа отдельным субагентом с чистым контекстом.
6. Коммит или PR, обновление `progress.md` и `balance.md`, «промпт следующей сессии»: какая задача дальше, какие решения приняты, где лежат документы.
7. Мерджишь сам, прочитав дифф.

**Контекст**

- `/clear` между несвязанными задачами.
- Сессия пошла не туда — начать заново с уточнённым промптом, а не чинить в загрязнённом контексте: каждое сообщение пересылает всю историю, включая неудачные попытки.
- Перед компакцией состояние задачи записывается в файл.

**Git**

- Короткие ветки, частые коммиты; `main` движется только через merge (закреплено hook).
- Тяжёлые прогоны (бот на сотнях сидов) идут в отдельном worktree в фоне.
- Параллельные сессии — только в разных worktree и по непересекающимся файлам.

**Раз в неделю**

- 30+ минут игры на целевом устройстве на production-сборке.
- Аудит самого процесса субагентом-критиком. Первый аудит — на второй день, а не на седьмой.
- Подрезка CLAUDE.md и правил.
- Каждый инцидент недели превращается в правку тулинга как можно ниже по лестнице: hook или скрипт, а не фраза в промпте.

## 6. Агенты и расширения

Один основной агент плюс несколько субагентов, у каждого из которых ценность одна — чистый контекст без допущений автора. «Студии» из десятков ролей — это одна модель с разными промптами, а их поддержка сама становится проектом; из шаблонов вроде Claude Code Game Studios брать идеи, не шаблон целиком.

**Субагенты**

| Роль | Задача | Когда запускать |
| --- | --- | --- |
| Ревьюер диффа | Корректность, дублирование, нарушение границ `sim`/`render`, лишние абстракции | Перед каждым PR |
| Автор тестов | Тесты по нумерованным правилам brief, не по реализации | До реализации фичи |
| Критик-плейтестер | «Холодная» оценка по метрикам бота и скриншотам; можно дать персону целевого игрока | После значимых изменений геймплея |
| Аудитор процесса | Что в CLAUDE.md, правилах и hooks мешает или не работает | Раз в неделю |

Роли делить по вопросу, на который агент отвечает, а не по артефакту, который он производит.

**Skills** (процедуры, которые иначе забываются к третьей сессии)

| Команда | Что делает |
| --- | --- |
| `/next` | Берёт следующую задачу из `progress.md` или последнего PR |
| `/ship` | Ревью, полный check, changelog, PR, промпт следующей сессии |
| `/brief` | Синхронизирует brief с принятыми решениями |
| `/bot` | Баланс-прогон с сохранением результата, без повтора уже сделанного |
| `/playtest-report` | Раскладывает твои заметки плейтеста на дизайн / баланс / баги / полировку |

**Hooks**

| Событие | Действие | Когда заводить |
| --- | --- | --- |
| После правки `*.ts` | prettier + `eslint --fix` на изменённом файле | День 0 |
| Перед git-командой | Запрет коммита и пуша в `main`, запрет force push | День 0 |
| Перед коммитом | Запрет коммита с ошибками линта и типов | День 0 |
| Перед тяжёлым прогоном | Отказ, если уже идёт бот-прогон | После первого инцидента |
| Старт сессии | Что уже запущено, последние метрики гейта | Когда появится бот |

Сообщение отказа hook читает агент, поэтому в нём пишется, что делать вместо запрещённого («заведи ветку»).

**MCP.** Playwright MCP: навигация, консоль, скриншоты, клики по координатам в canvas (`--caps=vision`). Для игры на three.js других серверов на старте не нужно.

**Модели.** Источники расходятся. Схема «директор + исполнители»: сильная модель на план, архитектуру, многофайловые рефакторинги и ревью, младшие на рутинную реализацию и статус-проверки. Альтернатива от создателя Claude Code: всё на самой сильной модели, потому что меньше переделок. Выбор определяется лимитом подписки.

**Автономные прогоны.** `--dangerously-skip-permissions` только в контейнере без лишнего доступа: контейнер и есть граница безопасности. Следить за лимитами: в одном из кейсов 71% месячных токенов ушло за первые 3 дня.

## 7. Верификация

Проверки идут от дешёвых к дорогим; задача не считается готовой, пока не пройден слой, который способен поймать её тип ошибки.

| Слой | Инструмент | Что ловит |
| --- | --- | --- |
| 1. Типы и линт | `tsc --noEmit`, eslint | Синтаксис, типы, нарушение границ модулей |
| 2. Юнит-тесты ядра | vitest; каждое нумерованное правило brief — отдельный тест | Ошибки правил игры |
| 3. Smoke | Playwright на production-сборке, N кадров | Ошибки консоли, падения, превышение бюджета `renderer.info` |
| 4. Скриншот | Playwright + odiff против эталона | Визуальные регрессии |
| 5. Бот + quality gate | Бот поверх команд, метрики в `results.json`, вердикт скриптом | «Тесты зелёные, игра неиграбельна» |
| 6. Баланс на сотнях и тысячах сидов | «Сильный» бот, перебирающий легальные ходы | Перекосы экономики и сложности |
| 7. Человек | Целевое устройство, production-сборка | Feel, эргономика, «весело ли» |

**Скриншоты**

- Всегда с критерием приёмки («игрок, пол и HUD видны при ширине 360 px»), не «посмотри, как выглядит».
- Агенту отдаётся процент расхождения от odiff и кадрированный фрагмент, а не два полных кадра: сырое сравнение засоряет контекст.
- Снимать на production-сборке через Playwright, не через `toDataURL`. Без GPU браузер запускается с `--enable-unsafe-swiftshader`.
- Сцена детерминирована: фиксированный сид, виртуальное время, заданный номер кадра.

**Quality gate.** Скрипт читает `results.json` и выдаёт GO / CONDITIONAL / NO-GO по трём ярусам:

1. Стабильность: прогон завершился без ошибок.
2. Коридор баланса: ключевые метрики внутри заданных границ.
3. Регрессия: падение метрики больше чем на 50% относительно последнего GO означает NO-GO.

Метрики и границы задаются под свой жанр. Образец из [гейта yurukusa](https://dev.to/yurukusa/why-your-ai-agent-needs-a-quality-gate-not-just-tests-42eo) для survivors-like: урон ≥ 1, HP не ниже 10%, интервал левел-апа 8–35 с, плотность врагов. Метрики «feel» оттуда же: плотность действий ≥ 2/с, «мёртвое время» < 20%, частота наград ≥ 0,2/с. Гейт ловит перекос в обе стороны, включая случай, когда агент «перекорректировал» сложность.

**Чего агент не видит**

- Ощущение удара, тайминги, отклик управления.
- Эргономику тача: в кейсе Eleven Labs при 1 087 зелёных тестах игра на телефоне была почти неиграбельна.
- Баги, существующие только в production-сборке.
- Билды, которые проходят гейт, но человек забраковал бы за 30 секунд.

## 8. Ассеты и контент

Арт-направление задаёшь сам; агент надёжен в том, что выражается кодом, и слаб в моделировании.

- **Кодом:** примитивы и процедурная геометрия, шейдеры, процедурный звук через Web Audio. По умолчанию результат выглядит «медианно» и безлико, поэтому стиль должен быть записан заранее.
- **Арт-библия** (`docs/art-bible.md`): палитра с конкретными цветами, свет, масштабы, запреты. Это якорь стиля и для шейдеров, и для внешней генерации.
- **Плейсхолдеры:** соглашение об именах и замене, чтобы финальный ассет подменялся без правки кода. Правила импорта лежат в `.claude/rules/assets.md`.
- **Внешняя генерация** (спрайты, GLB, музыка, SFX через MCP или CLI сторонних сервисов): общая проблема — неконсистентный стиль. Лечится референсом в каждом запросе и отдельным ассетом на объект.
- **Не делать:** моделирование в Blender через агента; по отзывам результат плохой.
- **Проверка:** отсутствующие текстуры и сломанные материалы ловятся скриншот-тестом и ошибками консоли в smoke.

## 9. Антипаттерны

| Антипаттерн | Почему возникает | Лекарство |
| --- | --- | --- |
| «Тесты зелёные — значит готово» | Тесты проверяют правила, а не играбельность | Quality gate + еженедельный плейтест руками |
| Доверие уверенному тону | Агент отчитывается по собственной уверенности | «Готово» принимается только с выводом команд проверки |
| Большие PR | Агент пишет быстро, ревью на большом диффе слабое | Один вертикальный срез на PR |
| Потеря контакта с кодом | Весь код пишет агент, диффы не читаются | Читать каждый дифф ядра; каркас писать самому |
| Дрейф терминов и правил | Каждая сессия начинает с нуля | Glossary, brief как источник истины |
| Дублирование и многословный код | Агент «идёт длинным путём» | Правило «минимальный дифф», ревьюер ищет дубли |
| Галлюцинации API three.js | Модель помнит другую версию | Пин версии, список удалённых API в правилах, `tsc` в hook |
| Оверинжиниринг обвяза | Шаблоны с десятками агентов выглядят солидно | Новый hook, skill или агент только после инцидента |
| Раздутый CLAUDE.md | Правила только добавляются | Еженедельная подрезка, перенос в `rules/` и hooks |
| Починка в загрязнённой сессии | Жаль потраченного контекста | `/clear` и новый промпт с учётом узнанного |
| Надежда на повторяемость | Один промпт даёт разные реализации | Решения фиксируются в ADR и тестах |
| Принять всё предложенное | Генерация дешёвая, каждое «да» становится долгом | Отклонять фичи вне пилларов brief |
| Вложения в арт до проверки фана | Агент не знает, весело ли | Throwaway-прототип на примитивах в первую неделю |

Узкие места при такой разработке — ревью, плейтест и поиск игроков, а не скорость написания кода: у задокументированных соло-кейсов выручка составила $1–5 за месяц.

## Источники и доказательность
